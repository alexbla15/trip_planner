# Task: Add Residence — pick from existing residences in the same country

Status: done
Track: B
Track reason: reuses the existing search-then-create-fallback pattern already built for regular attractions (`AttractionSearchModal` + `NewAttractionModal`) and the existing trip-schedule-override mechanism (`IScheduleEntry`) — no new visual pattern, just extending both to cover residences.

## Problem
Adding a regular attraction to a trip is a two-step flow: `AttractionSearchModal` lets the user search/pick an existing attraction in the trip's country first, with a "Create new attraction" fallback. Adding a residence skips straight to `AddResidenceModal`, a pure create form — there's no way to reuse an existing residence (e.g. the same hotel used on an earlier trip).

Naively wiring "pick existing" the same way as regular attractions has a real data-corruption risk: `checkInDate`, `checkOutDate`, and `price` currently live on the shared `Attraction` document itself, not per-trip. If picking an existing residence just resolved `existingAttractionId` and let the create-branch fields silently apply (or worse, overwrote the shared document's dates), a second trip reusing the same hotel would corrupt or lose the first trip's stay dates. (Confirmed via investigation: the backend's `existingAttractionId` branch in `POST /api/trips/[id]/attractions` currently ignores `checkInDate`/`checkOutDate`/`price`/`notes`/`residenceType` entirely — they're only applied on the "create new" branch.)

The chosen fix (confirmed with user): picking an existing residence reuses the *place* (name, city, country, coordinates, `residenceType`) but the user still enters check-in/out dates and price for **this trip** — stored per-trip, not overwritten onto the shared document. This mirrors how regular attraction scheduling already works: `Trip.schedules` (a per-attraction-per-trip map, see `IScheduleEntry` in `src/models/Trip.ts`) already carries trip-specific `plannedDate`/`plannedTime`/`price`/`currency`/`notes` overrides distinct from the shared document — this task extends that existing mechanism with two new fields (`checkInDate`/`checkOutDate`) rather than introducing a new one.

## Goal
A user adding a residence can search and pick an existing residence (by name, scoped to the trip's country) the same way they can for regular attractions, then supply this trip's own check-in/out dates and price — without ever overwriting another trip's stay data for the same shared residence document.

## Requirements
- **Schema**: add `checkInDate?: string` and `checkOutDate?: string` to `IScheduleEntry` (`src/models/Trip.ts`) and its Mongoose sub-schema, alongside the existing `price`/`currency`/`notes` fields there.
- **Backend** (`POST /api/trips/[id]/attractions`, `src/app/api/trips/[id]/attractions/route.ts`): when resolving via `existingAttractionId` (the "pick existing" path), write `checkInDate`/`checkOutDate`/`price`/`currency`/`notes` from the request body into the `scheduleEntry` object (alongside the existing `plannedDate`/`plannedTime`) — **not** onto the shared `Attraction` document. The "create new" branch keeps writing these onto the new document as it does today (that document has no other trip depending on it yet).
- **Read side**: wherever a residence's `checkInDate`/`checkOutDate`/`price` are formatted for display (check `formatAttraction` in `src/models/Attraction.ts` and how `TripDetailClient.tsx`/`ResidencesList.tsx` read these fields), prefer the trip's schedule-entry override over the shared document's own value when a per-trip override exists for that attraction id — same pattern already used for `plannedDate`/`plannedTime`. Trace how existing residence display currently sources these three fields before changing this, since the shared-document values are the ones existing residences (created before this change) will still be using — those must keep working with no override present.
- **Frontend — pick-existing step**: give residences the same two-step flow attractions already have. Reuse `AttractionSearchModal` (add a prop to filter results to `subtype === "residence"` client-side, since `GET /api/attractions` has no subtype query param today — client-side filtering on the existing `subtype` field is sufficient, no need to add a backend param for this alone) rather than building a new search component. Default/preset the category filter to "Accommodation" if that's a clean way to pre-narrow results (verify `TYPE_CATEGORIES.Accommodation` in `src/components/NewAttractionModal/attraction.constants.ts` lines up with residence attraction types before relying on it).
- When a user picks an existing residence from that search step, open `AddResidenceModal` pre-filled with the picked place's `name`/`country`/`city`/`coordinates`/`residenceType` (and `existingAttractionId` carried through to the save payload), with `checkInDate`/`checkOutDate`/`price` left blank for the user to fill in for this trip — do not prefill those three from the picked document.
- Wire `TripDetailClient.tsx`'s "Add Residence" button to open the new search-existing step first, with a "Add new residence instead" fallback that opens `AddResidenceModal` exactly as it does today (blank).
- Update `swagger.yaml` for the `Trip`/schedule-related schema additions (`checkInDate`/`checkOutDate` on whatever schema documents `POST /api/trips/{id}/attractions`'s request body / the schedule shape).

## Constraints
- Never write `checkInDate`/`checkOutDate`/`price`/`notes` from a "pick existing" submission onto the shared `Attraction` document — only onto that trip's schedule entry. This is the specific bug this task exists to avoid.
- Existing residences created before this change have no schedule-entry override yet and must keep displaying correctly from the shared document's own fields (no override present = fall back to the document, same as `plannedDate`/`plannedTime` already do elsewhere).
- Do not change how regular (non-residence) attractions or flights behave.

## Out of scope
- Migrating existing residences' `checkInDate`/`checkOutDate`/`price` off the shared `Attraction` document — they stay there as the "no override" fallback; only new picks-of-existing get the schedule-entry treatment.
- Adding a `subtype` query param to `GET /api/attractions` (client-side filtering on the search modal's existing results is sufficient at current data volumes).
- Any change to how flights are added (out of scope, different subtype, different nuance).

- **Known limitation surfaced during implementation, flagged rather than silently expanded into scope**: `handleResidenceUpdate` (the pencil/edit-a-residence flow, unrelated to this task's "pick existing" flow) still calls `PUT /api/attractions/{id}` and writes `checkInDate`/`checkOutDate`/`price`/`notes` directly onto the shared document — meaning editing a residence that happens to be reused across multiple trips still corrupts the other trip's stay data. This is a pre-existing risk (predates this task, not introduced by it) of the exact same shape as the one this task fixed for the *add* flow. Fixing it would mean routing residence edits through a schedule-entry-aware update path instead of the generic attraction PUT, which is a larger, separate change — recommend a follow-up task.
