# Task: Turn a Dropped Pin Into an Attraction, and Add an Existing Attraction to Your Trip

Status: done

Track: A
Track reason: Two new interactions on Explore's map — (1) creating an attraction from an ephemeral measure-tool pin needs a "create" (not "edit") variant of `NewAttractionModal`'s copy/title, which doesn't cleanly exist today since passing partial `initialData` flips it into edit mode; (2) picking one of "my trips" to link an attraction into is an entirely new UI (no trip picker exists yet).

## Problem
Two related gaps in Explore's attraction/pin interactions:
1. The measure-distance tool's dropped/searched pin (`ExploreClient.tsx`, `MeasurePoint` with `kind: "custom"`) is purely ephemeral — there's no way to turn it into a real saved attraction without leaving the tool and manually re-entering coordinates elsewhere.
2. Clicking an existing attraction on Explore opens `AttractionDetailModal` (view, and edit if you own it — from an earlier task today) but there's no way to add that attraction to one of your own trips' schedules. The underlying capability already exists (`addAttractionToTrip` with an `existingAttractionId` — used elsewhere for exactly "link a known attraction to a trip without re-creating it"), it's just not exposed from Explore.

## Goal
1. Clicking a custom/dropped pin offers "Add as new attraction," opening `NewAttractionModal` correctly labeled as a *create* flow (not edit), pre-filled with that pin's coordinates and (where resolvable) reverse-geocoded city — saved via the existing `createAttraction` call, same as Explore's existing "Add Attraction" button.
2. Clicking an existing attraction offers "Add to my trip," letting the user pick from trips they own or collaborate on, then links the attraction into that trip via the existing `existingAttractionId` linking path — no re-creation, no name-based dedup risk.

## Requirements

### Feature A — pin → new attraction
- Add an "Add as new attraction" action reachable from a custom measure-pin (e.g. a popup/tooltip action on the pin, or a button in the measure panel when a custom pin is present) — only relevant to `kind: "custom"` points, not `kind: "attraction"` points (those already exist).
- `NewAttractionModal` needs a way to be opened in genuine **create** mode while still pre-filling `coordinates` — passing today's `initialData` prop flips it into edit-mode copy ("Edit Attraction" title, `isEditMode = Boolean(initialData)`), which is wrong for this flow. Add a way to pre-fill just the coordinates (and reverse-geocoded city, if resolved) without triggering edit-mode labeling — e.g. a new prop (`initialCoordinates`, or a `mode` flag) rather than repurposing `initialData`.
- Before opening the modal, reverse-geocode the pin's coordinates (`reverseGeocode` in `src/services/geocoding.service.ts`, already used internally by the modal's own `MapPicker` for user-driven coordinate changes — don't assume that internal effect fires for a pre-supplied coordinate; call it explicitly here) to pre-fill city where possible. Country is not auto-filled by geocoding anywhere in the existing code — leave it for the user to select, same as today's behavior elsewhered.
- On save, use the existing `createAttraction` flow exactly as Explore's current "Add Attraction" button does (`handleAddSave` in `ExploreClient.tsx`) — same toast/state-update conventions.
- After successfully creating the attraction, the custom pin's job is done — clear it from the measure tool (or leave it and let the user manually exit measure mode, developer's call, but don't leave a stale ephemeral pin pointing at now-duplicate data without at least offering to clear it).

### Feature B — existing attraction → add to trip
- Add an "Add to my trip" action in `AttractionDetailModal` (footer, alongside the existing conditional "Edit attraction"/"Edit time & duration" buttons — same visual recipe) — visible whenever the user is logged in (not gated by ownership; adding someone else's shared attraction to your own trip is the whole point of a shared-attraction model, unlike editing).
- Build a small trip-picker modal (reuse `AttractionPickerModal`'s list/portal/backdrop structure as the template — filterable list, `role="listbox"`/`role="option"`, click-to-select, footer confirm) listing the current user's trips via the existing `listTrips(token)` call, which is **already scoped server-side to trips the user owns or collaborates on** — no extra client-side permission filtering needed.
- On confirming a trip, call the existing `addAttractionToTrip(tripId, token, { existingAttractionId: attraction._id })` client service (already supports this exact "link by known id" path server-side, per `src/lib/services/attractions.service.ts`'s `existingAttractionId` branch — no backend change needed) — then close the picker and show a success toast (`useToast()`, matching the app's established convention) naming which trip it was added to.
- Handle the "already in that trip" case gracefully — the backend already treats a repeat link as a 200 no-op rather than an error (confirmed in the service logic); reflect that as a success-toned message too ("Already in <trip name>" or similar), not an error.

## Constraints
- Feature B must use the `existingAttractionId` linking path, not the name-based dedup/create path (`AttractionSearchModal`'s flow) — using the wrong path risks creating an unwanted duplicate `Attraction` document instead of linking the existing one.
- Feature A must not silently mislabel the modal as "Edit Attraction" for what is actually a new attraction being created from a pin — this is a real, confirmed UX bug risk with the naive approach (passing `initialData`), not a hypothetical.
- Reuse `AttractionPickerModal`'s structural pattern for the trip picker rather than inventing a new modal shell.

## Out of scope
- Multi-select (adding one attraction to several trips at once)
- Any change to how attractions are created from the existing "Add Attraction" sidebar button (already works, not being touched)
- Persisting which trip an attraction "belongs to" beyond the existing `attractionIds`/`schedules` linking already used everywhere else

## Follow-up requested during review
`TripPickerModal` now takes a `country` prop and filters the trip list to only trips matching the attraction's country (`ExploreClient.tsx` passes `selectedAttraction.country`) — an attraction is tied to a specific place, so it shouldn't be addable to a trip going somewhere else. Distinct empty state added for "you have trips, just none to this country" vs. "you have no trips at all." Verified live: created one trip in Georgia and one in Hungary, confirmed the filter for a Georgia attraction includes only the Georgia trip; cleaned up both test trips afterward.

## Bug found during review: "iceland ones do not work"
User report led to a real bug, not an Iceland-specific one — my earlier "verified live" claim only tested the country-filter logic in isolation via `curl`, never the actual click sequence in the browser, which is exactly the gap that caused this to slip through. `AttractionDetailModal`'s "Add to my trip" button calls `onAddToTrip(); onClose();` together — `onClose` clears `selectedAttraction` to `null` in the same React batch that opens the picker, so by the time `TripPickerModal` rendered, `country={selectedAttraction?.country ?? ""}` had already gone empty — meaning **no country's trips ever matched**, not just Iceland's. (The user likely hit this first with an Iceland attraction; it would have failed identically for Georgia, Hungary, or any other country too, despite my earlier curl-based check appearing to confirm the filter worked.)
- Fix: added a dedicated `attractionForTripPicker` state in `ExploreClient.tsx`, captured from `selectedAttraction` at the moment "Add to my trip" is clicked (before `onClose` has a chance to null it out), decoupling the picker's target from the detail modal's own lifecycle. `handleTripSelect` and the `country` prop now both read from `attractionForTripPicker`, not `selectedAttraction`.
- `tsc --noEmit` clean. This class of bug (event-handler-order state race) isn't something a `curl`/API-level check can catch — confirmed via careful reading of the exact click-handler chain (`AttractionDetailModal.tsx` → `ExploreClient.tsx`) rather than assumed fixed by symptom-matching.
