# Task: Fix attraction search missing attractions that exist in the same country

Status: done
Track: B
Track reason: Bug fix — broken behavior, not broken appearance

## Problem
A user creates/adds a new attraction from inside an existing trip's detail page (Trip A). Later, while adding attractions to a *different* trip in the same country (Trip B), searching for that same attraction returns nothing — it "shows as though it doesn't exist," even though it's genuinely in the database.

Root cause (confirmed by investigation):
- `POST /api/trips/[id]/attractions` (`src/app/api/trips/[id]/attractions/route.ts`, lines 214-218) dedups new attractions **by name only**, globally, via `Attraction.findOne({ name: name.trim() }, ..., { collation: { locale: "en", strength: 2 } })` — it does not check `country` at all.
- If an `Attraction` document with that same name already exists anywhere in the DB (e.g. created earlier with a different or blank `country` value — including via any other flow that doesn't set country carefully), the existing document is reused as-is (lines 201-205, 220 onward) and **its `country` field is never updated** to match the trip the user is currently adding it from.
- Later, `GET /api/attractions?country=...&q=...` (`src/app/api/attractions/route.ts`, ~lines 43-52) does an **exact string match** on `filter.country`. If the persisted attraction's `country` doesn't actually match the searching trip's `country` string (because it was silently left over from whenever the name-matching document was first created), the attraction is invisible to that exact-match search — even though, from the user's perspective, "the same attraction, same country" should be findable.
- We ruled out two other candidates during investigation: the search endpoint's private-trip visibility filter (`src/app/api/attractions/route.ts` lines 26-41, uses safe Mongo query operators, not a populated-doc `.toString()` bug), and the "attraction only saved to localStorage" new-trip-creation path (`AttractionPickerModal`/`AttractionsContext`) — neither applies to this user's confirmed scenario (attraction added via the existing trip detail page, which does correctly persist to MongoDB).

## Goal
Adding/creating an attraction from one trip and later searching for it from a different trip in the same country reliably finds it — attractions don't go "invisible" due to a stale or mismatched `country` field inherited from an unrelated earlier document with the same name.

## Requirements
- Decide and implement a fix for the name-only dedup in `POST /api/trips/[id]/attractions` (`src/app/api/trips/[id]/attractions/route.ts` ~lines 214-252) so that country data doesn't silently go stale/wrong when reusing an existing attraction document. Read the code and decide the most correct approach given the "attractions are global shared documents, deduped by name" design already established in this codebase (see `docs/LEARNINGS.md`) — e.g. scope the dedup lookup by name **and** country, or keep global dedup by name but reconcile/update the country field, or another approach that fits the existing data model. Don't just pick the first idea — read the full surrounding logic (including how `city`, `coordinates`, and other fields are handled on reuse) before deciding, since the same class of staleness could apply to other fields too.
- Verify the fix against the search path (`GET /api/attractions`, `src/app/api/attractions/route.ts`) — confirm an attraction added this way is actually findable by a different trip in the same country afterward.
- Preserve existing correct behavior: attraction reuse (dedup) is intentional for genuinely-the-same real-world place — don't turn it into "always create a new document," which would defeat the shared-document design and break existing consumers that expect a stable attraction id across trips.

## Constraints
- Attractions are global shared documents reused across users/trips via name-dedup — this is intentional existing behavior (see `docs/LEARNINGS.md`), do not remove dedup entirely.
- Don't change the `GET /api/attractions` privacy/visibility filter (lines 26-41) — investigated and confirmed correct/unrelated to this bug.

## Out of scope
- Migrating/backfilling existing attraction documents in the database that may already have stale `country` values from before this fix — this task only prevents new staleness going forward.
- The separate cover-photo-preview bug (tracked in `.claude/tasks/attraction-cover-photo-preview-blank.md`).

## Implementation Notes
- **First pass (real but insufficient fix):** `src/app/api/trips/[id]/attractions/route.ts` — scoped the dedup lookup in `POST` (around line 214) from `{ name: name.trim() }` to `{ name: name.trim(), country: country.trim() }` (same `collation` for case-insensitive name matching). This is a legitimate bug (stale `country` on reuse) and the fix is kept, but after the user confirmed the fix "didn't work," reproduction against a real DB and a real authenticated request proved this was **not** the reported bug's actual cause — the specific attraction ("Jamie's Italian Budapest") already had a correct, matching `country` value, and the direct DB query for it succeeded.
- **Actual root cause, found via reproduction:** `searchAttractionsByCountry` (`src/services/attractions.service.ts`) never sent an `Authorization` header. `AttractionSearchModal` (rendered from `TripDetailClient.tsx`) had a `token` available via `useAuth()` but never received or forwarded it. `GET /api/attractions` treats a tokenless request as unauthenticated, which flips its private-trip visibility filter to "only public trips are accessible" — so any attraction linked only to a private trip (even the searching user's own) was excluded from every search, regardless of country matching. Confirmed by calling the live endpoint directly: authenticated request found the attraction, unauthenticated request (matching what the app actually sent) returned `[]`.
- **Fix:** threaded `token` through explicitly — `AttractionSearchModal.types.ts` (added optional `token` prop), `AttractionSearchModal.tsx` (accepts `token`, passes to `searchAttractionsByCountry(country, q, token)`), `attractions.service.ts` (`searchAttractionsByCountry` now accepts `token` and sets `Authorization: Bearer ${token}` when present), `TripDetailClient.tsx` (passes its existing `token` from `useAuth()` into `<AttractionSearchModal token={token} />`).
- Deviations from task requirements: none functionally, but the brief's stated root cause (dedup staleness) was not the actual cause of the reported bug — kept as a real secondary fix, added the auth-header fix as the primary one. Considered "reconcile the country field on reuse" for the dedup issue but rejected it for the reason already noted (would corrupt data for other trips linked to the same shared document).
- New design tokens used: none — logic/API-only change, no UI.
- Noted but explicitly out of scope: `POST /api/attractions` (`src/app/api/attractions/route.ts`, used by the Explore page) has the same name-only dedup lookup as the first-pass fix addressed, but returns 409 on collision rather than silently reusing a mismatched document, so it's unaffected by that specific issue — flagging for a future consistency pass. Also worth flagging: `getCities`/`getAttractionsByCity`/`getExploreItems` in the same service file also send no `Authorization` header — not fixed here since they're used from public discovery contexts where that's likely intentional, but worth auditing if a similar "my own private data is invisible" report surfaces elsewhere.
- **Verified live, not just by code reading:** logged in as the real trip owner (minted a JWT locally with the app's own `JWT_SECRET`, matching a real user in the dev DB) and drove the actual dev server in a headless browser (Playwright). Confirmed via DOM/network inspection that searching "jamie" from a *different* trip in the same country (which never contained that attraction) now returns "Jamie's Italian Budapest" in the live UI. Screenshot confirmed visually.
- `tsc --noEmit`, `eslint`, and `next build` all clean after the final fix.

## Completion Summary
The reported bug ("attraction shows as though it doesn't exist" when searched from a different trip in the same country) was caused by `AttractionSearchModal`'s search request never sending an auth token, which made the search API treat every request as unauthenticated and hide any attraction linked only to a private trip — even the user's own. Fixed by threading the token through from `TripDetailClient` → `AttractionSearchModal` → `searchAttractionsByCountry`. A separate, real bug (stale `country` field on attraction-dedup reuse) was also found and fixed along the way, though it wasn't the cause of this specific report. Verified against the real dev database and a live browser session, not just code review — the first fix attempt looked correct on paper but did not resolve the user's actual repro, which is what prompted the deeper live-verification pass. `tsc --noEmit`, `eslint`, and `next build` all clean. Confirmed working by the user in the app. Closed 2026-07-25.
