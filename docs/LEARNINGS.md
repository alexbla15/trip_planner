# Learnings

## Product

- **Dashboard is the root page (`/`)** — future tasks that add new top-level screens (Trip Detail, Explore page, Auth) should be separate routes under `src/app/`, not added to `page.tsx`.
- **Mood tags are the core UX differentiator** — every feature touching discovery or trip display should surface mood tags prominently; they are not decorative.
- **Interactive chips must have icons** — any toggleable chip (mood tags, attraction types) should pair an icon with its label. Text-only chips look unfinished and fail the design-system "Buttons must include icons" rule.
- **Shared entity stores belong in layout-level context** — attractions (and future entities like trips) are needed across multiple pages and entry points; wire them through a React context in `Providers.tsx` from day one, not as ad-hoc prop drilling.
- **Navbar + Footer go in `layout.tsx`, not per-page** — placing them per-page causes duplication and means new routes launch without them. Move to layout once and done.
- **Don't assert "these are duplicates" in a task brief without having diffed them — say "these look like duplicates, verify and dedupe if so" instead:** the `shared-utils-extraction` brief stated `CalendarSection.utils.ts`'s `attractionEndMins` was one of three copies of the same function and should be merged. It wasn't a true duplicate (different edge-case behavior around missing data and minimum durations), and the brief's confident phrasing almost caused a behavior-changing merge. Same-named helpers found via grep/audit are a lead to investigate, not a fact to state as settled in the requirements.
- **In a sequenced goal, a later task's brief can go stale before it's even started** — `nextjs-practice-fixes`'s brief cited exact file:line locations for 6 raw `<img>` tags, gathered during the original `/qc` audit before tasks 1–3 (service layer, utils, barrels) touched nearly every file in the codebase and shifted line numbers. It also undercounted (6 vs. the actual 10, across 4 files vs. the actual 7) because the original audit's own search pattern had a blind spot. When a goal's tasks are sequenced with heavy intermediate refactors between intake and implementation, treat any brief's specific file:line citations as "here's roughly where to look," not "here's the exhaustive list" — the developer should always re-verify scope with a fresh search immediately before implementing, not trust the brief's enumeration.
- **Don't prescribe an error-handling/API convention in a task brief for a codebase-wide refactor** — when scoping a task like "extract a service layer," state the goal ("every fetch call goes through a service function") but leave the specific error-handling convention (throw vs. return-Response, etc.) as an implementation decision made by reading the actual call sites, not dictated up front. The `data-fetching-service-layer` task's brief specified "throw on non-OK" without having surveyed the ~30 call sites first, which led to an overcautious first pass (blanket raw-`Response` returns) that needed a full correction round. Better: ask the developer to default to parse-and-throw and document exceptions, rather than picking the convention in Step 2 before anyone has read the code.
- **A single vague bug report ("X couldn't load") can hide two stacked bugs, where fixing the first only reveals the second** — `trip-detail-orphaned-reference-crash` started as one reported symptom (a crash), but after that root cause was fixed, the user's very next reload hit a second, unrelated pre-existing bug (a broken ownership check) that had been masked by the crash happening earlier in the same request. Don't treat "the diagnosed root cause is fixed" as equivalent to "the reported symptom is resolved" — ask the user to re-verify the actual originally-reported scenario after a bug fix, not just confirm the fix matches the diagnosis, and be ready to keep investigating within the same task if the symptom recurs in a new form.
- **A plausible, well-evidenced root cause found by reading code (even with grep/DB spot-checks) can still be wrong — only a live repro against real data proves it** — `attraction-search-country-mismatch` and `attraction-cover-photo-preview-blank` both shipped a first fix that was internally consistent, passed `tsc`/`eslint`/`next build`, and matched a specific documented LEARNINGS.md pattern (dedup staleness; `onLoad`-only cache bug) — but neither was the actual cause of the user's report. The real causes (a missing `Authorization` header on one call site; `next/image`'s default `loading="lazy"` deadlocking with a hidden-until-loaded preview) only surfaced after driving the real dev server with a real logged-in session against real DB records. Static checks (`tsc`, `eslint`, `next build`) prove the code is well-formed, not that it fixes the reported bug. For a bug report specific enough to name real data (an attraction name, a specific flow like "Edit Attraction"), reproduce against that real data/flow before asking the user to confirm — don't rely on a theory that merely "explains the symptom" on paper, and don't ask for confirmation a second time without having verified yourself first if the first "fix" turned out to be wrong.

## Development
- **Mongoose `save()` silently skips writes on documents with `Map` fields:** Calling `.save()` after mutating a plain field (e.g. `isPrivate`) on a document that also has a `Map`-typed field (`schedules`) can no-op due to Mongoose change-detection misfiring. Always use `findOneAndUpdate` with an explicit `$set` for partial updates — it bypasses document-level dirty tracking entirely.
- **Collaborator subdoc: store only `userId`, join at read time:** Don't duplicate user `name`/`email` into embedded subdocs — they go stale. Store only `userId` (with `ref: "User"`) and chain `.populate("collaborators.userId", "name email")` on every query that calls `formatTrip`. Cast the populated field with `c.userId as unknown as { _id, name, email }` inside `formatTrip`.
- **Combo-box `onMouseDown` vs `onClick` for dropdown items:** Use `onMouseDown` on dropdown `<li>` items instead of `onClick`. The input's `onBlur` fires before `onClick`, closing the dropdown and swallowing the click. `onMouseDown` fires first and the selection goes through before blur closes the list.

- **Modal portal pattern:** Use `createPortal(modal, document.body)` with a `mounted` state gate (`useEffect(() => setMounted(true), [])`) to avoid SSR/hydration mismatch. Return `null` when `!mounted || !isOpen`. The `"use client"` directive on the modal shell is sufficient — sub-components in the same module graph inherit it without needing their own directive.
- **`@react-google-maps/api` + React 19:** Install with `--legacy-peer-deps`; the package works at runtime even though its peer-dep declaration lags behind React 19.
- **Leaflet in Next.js App Router:** Use `next/dynamic(() => import('./LeafletMapWidget'), { ssr: false })` to prevent SSR errors. The Leaflet CSS import (`import "leaflet/dist/leaflet.css"`) must live inside the dynamically-imported module. Fix default marker icons by calling `L.Icon.Default.mergeOptions({ iconUrl: ... })` at module scope inside that same file.
- **`next/link` as button replacement:** When a `<button>` is purely navigational (no form submission, no side-effect), replace it with `<Link href="...">` using the same CSS class. Link renders as `<a>`, so all existing CSS applies unchanged.
- **Mongoose model enum must match TypeScript union:** When adding a new `subtype` value (e.g. `"free-slot"`), update three places — the TypeScript interface in `src/types/`, the TypeScript interface in `src/models/`, AND the Mongoose schema enum. Missing either model location causes a `tsc --noEmit` type error on `Model.create({ subtype: "free-slot" })`.

- **CSS module tag color pattern:** When a component needs per-value dynamic colors (e.g. mood tag chips), define one CSS class per value in the module (`.tagHiddenGems`, `.tagInstagrammable`, etc.) and map tag strings → class names in a `.constants.ts`. This avoids inline styles entirely and keeps the hard "no inline style" rule intact.
- **Next.js Image with responsive cards:** For card components where the image must fill a responsive container, use `fill` prop + `position: relative; aspect-ratio: X/Y` on the parent wrapper — not explicit `width`/`height` props. This prevents CLS without hardcoding pixel dimensions.
- **Remote images require `remotePatterns` in `next.config.ts`** — must be configured for any external host (e.g. `images.unsplash.com`) before `<Image src="https://...">` works.
- **Client Components in App Router:** Only add `"use client"` to components that actually need `useState`/event handlers (e.g. filter section, mobile nav toggle, keyboard-interactive cards). Keep Server Components for all static/display components to reduce JS bundle.
- **Auth context in dashboard pages:** Server Components cannot call `useContext`, so a page that needs the logged-in user's name must either (a) be converted to a `"use client"` with a thin inner component, or (b) use a small client sub-component for the dynamic part. Pattern (a) is simplest while data still comes from static imports; switch to RSC + server fetch once real API wiring begins.
- **JWT route handlers — Node.js runtime:** `jsonwebtoken` uses Node.js `crypto`. Next.js App Router Route Handlers default to Node.js runtime, so no `export const runtime = 'edge'` needed. Do not add it or the import will break.
- **Mongoose model re-registration guard:** Always use `(mongoose.models.ModelName as Model<T>) || mongoose.model<T>('ModelName', Schema)` to prevent "Cannot overwrite model" errors during hot-reload in dev.
- **API shape migration — migrate the type, not the mapping:** When the API shape differs from a mock type (e.g. `_id` vs `id`, `moods` vs `tags`), update the shared type to match the API directly. An adapter/mapping layer adds indirection with no payoff in Next.js client components.
- **Self-fetching client components:** When a page's data depends on `useAuth().token`, the data-fetching component must be a Client Component using `useEffect`. Server Components cannot access context or tokens. Pattern: receive the `id` param as a prop from the (server) page, do the `fetch` + `useAuth` inside the Client Component.
- **Optional coverImage on TripCard:** Use a CSS gradient placeholder (`position: absolute; inset: 0; background: linear-gradient(...)`) when `coverImage` is undefined — renders cleanly without `<Image>` receiving a null src.
- **Next.js App Router nested dynamic segments:** You cannot have two different dynamic segment names at the same folder level (e.g. `api/trips/[id]` and `api/trips/[tripId]` would conflict). All nested routes under trips must use `[id]` as the trip param name to match the existing folder.
- **Mongoose model/type naming collisions:** If a file imports a TS interface and also exports a Mongoose model with the same name (e.g. `Attraction`), alias the import (`import type { Attraction as AttractionShape }`) to avoid TS2395 merge declaration errors.
- **Mood tag surface area:** The tag set lives in 6+ files (types, constants, two CSS modules, two forms, explore section, explore API, mock data). When updating tags, also check ExploreSection.tsx (local TAG_ICONS map) and the explore API route (fallback tag strings) — they are not covered by the shared constants import.
- **CSS-only toggle switch via `<button role="switch">`:** Implement as a `<button>` with `role="switch"` and `aria-checked`. Use a `::after` pseudo-element as the thumb; toggle between `left: 3px` (off) and `left: 23px` (on) with `transition`. No hidden checkbox needed — avoids form association complexity and works with keyboard/screen readers out of the box.
- **Collaborator access control via `$or` query:** Use `{ $or: [{ ownerId: userId }, { 'collaborators.userId': userId }] }` directly in the Mongoose `findOne`/`find` call — Mongoose auto-casts the string userId to ObjectId because the schema field is typed as `Schema.Types.ObjectId`. Avoids a separate post-fetch ownership check.
- **State merge after optimistic updates:** When a server PUT response is used to update client state, always merge calendar/scheduling fields (plannedDate, plannedTime, actualDuration*) from the *current* state item rather than blindly replacing with the server object. The server reflects DB state which may lag behind local optimistic changes.
- **Leaflet DivIcon icons in Next.js:** `renderToStaticMarkup` from `react-dom/server` can serialize Lucide React elements to SVG strings for use inside Leaflet `DivIcon` HTML. This works because the component is loaded with `ssr: false` via `next/dynamic`. The `leaflet.css` import must live inside the dynamically-imported component, not the parent.
- **403 vs 404 for private resources:** When a resource exists but the caller lacks permission, return 403 — not 404. Returning 404 conflates "doesn't exist" with "you can't see it", making the client unable to show a meaningful error. Pattern: fetch by ID first to check existence, then check access in code and return 403 `{ error: "This trip is private" }` if denied.
- **Explore / discovery pages must never show private content — no exceptions:** Even for the resource owner. A public discovery feed is unconditionally public; adding owner/collaborator carve-outs breaks the mental model and leaks intent. Always apply the `isPrivate: { $ne: true }` filter without any `$or` exceptions on Explore-style endpoints.
- **Shared attraction ownership check — use trip membership, not attraction ownerId:** Attractions are global shared documents; the same row is reused across users via name-dedup. A PUT handler that checks `ownerId === currentUser` silently 404s for non-creators. Correct access check: user owns the attraction OR `Trip.exists({ attractionIds, $or: [{ownerId}, {collaborators.userId}] })`.
- **MongoDB aggregation on ObjectId-ref arrays needs `$lookup` before `$group`:** When a schema field is migrated from `String[]` to `ObjectId[]` with a `ref`, any aggregation that `$unwind`s that field and `$group`s by it will produce ObjectId strings as `_id`, not human-readable names. Always add a `$lookup` immediately after `$unwind` to join the referenced collection, then `$group` by the resolved name field (e.g. `$typeDoc.name`).
- **Valhalla `status` field is unreliable as a success gate:** The `trip.status` field is absent in some Valhalla response versions; checking `data.trip?.status !== 0` silently discards valid routes (`undefined !== 0` is `true`). Check for the presence of legs (`data.trip?.legs?.[0]`) instead — `res.ok` already handles HTTP-level errors.
- **Icon picker / grid combobox — `onBlur` close via container `relatedTarget`:** For a picker that has a search input + a grid of focusable items, use `onBlur` on the wrapper `<div>` with an `e.relatedTarget` check (`containerRef.current?.contains(e.relatedTarget as Node)`) to close only when focus truly leaves the component — not when the user moves between the search input and a cell. Pair with `tabIndex={-1}` on grid cells (keyboard nav handled entirely in the search input) and `onMouseDown` + `e.preventDefault()` on cells to prevent focus transfer on click.
- **useMemo hooks before early returns — promote plain derived consts when needed:** If a new `useMemo` depends on a value that was previously a plain `const` after an early return, promote that plain const to a `useMemo` above the early return. Plain consts on empty arrays are cheap; the key constraint is that hooks can't be called conditionally.
- **Searchable combobox blur vs item click — use `onMouseDown` + `e.preventDefault()`:** When a `<input onBlur={close}>` is paired with a clickable list, `onBlur` fires before `onClick`, swallowing the click. Fix: put `e.preventDefault()` in `onMouseDown` on list items (and any button inside the open state like a clear button). This prevents the input losing focus; the `onBlur` only fires for genuine outside-clicks, which is exactly the desired "revert on outside blur" behavior.
- **Controlled search+chip component — forward inputRef for programmatic focus:** When extracting a search input into a shared component, add an optional `inputRef?: React.RefObject<HTMLInputElement | null>` prop and spread it onto the `<input ref={inputRef}>`. This lets callers (like a modal) auto-focus the input on open without the component needing to expose imperative handles.
- **API type vs category param mismatch — keep category filter client-side:** The attractions API `?type` param resolves a specific type name via Mongoose lookup; passing a category name returns nothing. When adding category filter to a search modal that already fetches attractions by text, apply the category filter client-side on the returned results — avoids a DB schema change and is accurate on the 20-item result set.
- **`useAttractionTypes` is a superset of `useAttractionCategories` for filter UI:** `useAttractionTypes` already returns `categories: string[]` and `byCategory: Record<string, AttractionTypeRecord[]>` — everything needed to render a category+type multi-select filter. `useAttractionCategories` returns `AttractionCategoryRecord[]` (objects with `_id`, `icon`, `color`, `order`) and is only needed when those extra fields are required. For pure string filter chips, prefer `useAttractionTypes()` and avoid the extra hook/API call.
- **Adding a new Mongoose schema field requires a dev-server restart, not just a save:** `mongoose.models.ModelName` (the re-registration guard from the bullet above) means the compiled schema survives Next.js Turbopack hot-reload across API route requests — only the route module gets re-evaluated, not the already-registered model. A brand-new field added to a schema (e.g. `attractionRef` on `Trip.schedules`' sub-schema) will be silently stripped by strict-mode on every write until the dev server process is restarted, even though `tsc`/lint pass and the code looks correct. Symptom: a field present in the in-memory object right before `$set`/`.save()` is simply absent when you re-read the document from the DB. If a newly-added field isn't persisting and the write code looks right, restart `next dev` before debugging further.
- **MongoDB aggregation for city list with coordinates:** Group attractions by city, avg lat/lng as centroid, count attractions: `{ $match: {"coordinates.lat": {$exists: true}} }, { $group: { _id: "$city", lat: {$avg: "$coordinates.lat"}, lng: {$avg: "$coordinates.lng"}, count: {$sum: 1} } }, { $sort: { count: -1 } }`. Returns useful map seed data without needing a separate cities collection.
- **Modals on Leaflet map pages need z-index ≥ 1000:** Leaflet's internal layer stack tops out at z-index 700 (popup pane). Any modal backdrop using `position: fixed` must use `z-index: 1000` or higher, otherwise it renders behind map markers and tooltips. The default `z-index: 200` matches Leaflet's tile layer and is invisible.
- **Pinned sidebar footer — don't use `position: sticky` inside a flex scroll container:** When a sidebar is both a flex container and the scroll container (`overflow-y: auto`), `sticky` children don't reliably pin. Instead, split into a `sidebarScrollArea` div (`flex: 1; overflow-y: auto; min-height: 0`) for scrollable content and a sibling `sidebarFooter` div (`flex-shrink: 0`) outside the scroll area. The sidebar itself gets `overflow: hidden`.
- **Floating overlay buttons on Leaflet maps need `z-index ≥ 1100` AND must not be at top-left:** Leaflet's zoom control renders at `position: absolute; top: 0; left: 0; z-index: 1000` inside the map container. Any floating button positioned over the map at the same corner with a lower z-index will be covered and untappable on mobile. Fix: move the button to `right: 12px` (top-right) and set `z-index: 1100`.
- **"Duplicate" helper functions found via `/qc`-style audits aren't always duplicates — diff them before deduping:** When consolidating same-named helpers into `src/lib`, read every copy in full before merging; two functions with identical names and near-identical bodies can still differ in a load-bearing way (e.g. `CalendarSection.utils.ts`'s local `attractionEndMins` had no minimum-duration floor and tolerated a missing `plannedTime`, while the "duplicate" version elsewhere applied a 30-min floor and asserted the field was set). Merging them would have silently changed alert-computation behavior for short-duration items. If the copies diverge in a way that matters, keep the odd one local (with a comment explaining why) rather than forcing a single shared implementation.
- **After moving a helper into `src/lib`, re-check for now-unused imports one function away, not just in the moved function itself:** If function A (moved) internally calls function B (also moved, e.g. `attractionEndMins` used inside `detectConflicts`), files that only called A directly will end up importing B unused once both live in the shared module — `tsc` won't catch this (it's just an unused import) but `eslint` will. Run lint immediately after a batch of moves, not just typecheck/build, to catch these.
- **Service-layer extraction — parse/throw internally by default; raw `Promise<Response>` only for genuinely divergent callers:** When moving scattered `fetch()` calls into `src/services/*.service.ts` modules, default each service function to parsing the response and throwing an `ApiError` (status + parsed body, see `src/services/http.ts`) on non-OK, returning typed data on success. Only keep a function returning the raw `Response` when you can point to a specific caller that needs it — different status-code branching (e.g. 403 vs 404), a caller reading a sibling response conditionally, or a caller that deliberately never checked `res.ok` (so throwing would newly skip logic that previously always ran, like a fire-and-forget `window.location.reload()`). Decide per function by reading its actual call sites, not by blanket caution — an earlier pass of this defaulted every function to raw-`Response` "to be safe," which was the wrong call. Also: not every screen calling an endpoint shows up in a QC/grep audit if the audit script's file list is incomplete — `src/app/page.tsx` and `src/app/analytics/AnalyticsClient.tsx` both had raw `fetch()` calls that were missed by the initial audit and only surfaced by re-grepping for `fetch(` after the "known" call sites were migrated.
- **Nominatim geo boundary proxy — server-side module-level cache:** Create a Next.js route handler that calls `https://nominatim.openstreetmap.org/search?q=…&polygon_geojson=1` and caches results in a `Map` at module scope. Set `next: { revalidate: 86400 }` on the fetch. Pick the first feature whose geometry type is `Polygon` or `MultiPolygon`. In the client, fire one request per country in parallel (parallel requests hit the server, which serializes Nominatim calls via cache misses naturally); polygons appear incrementally as each resolves.
- **Grepping for `<img` to audit raw `<img>` usage must not assume trailing whitespace on the same line:** A pattern like `<img\s` misses the very common multi-line JSX form `<img\n  src={...}\n  ...\n/>`, where `<img` sits alone at end-of-line. Use `<img(\s|>)` or just `<img` with no anchor, and always re-grep fresh rather than trusting a prior audit's file/line list — it silently undercounted real occurrences by 2 files and 4 instances in the `nextjs-practice-fixes` task.
- **`next/image` + arbitrary user-pasted URLs: use `unoptimized`, not a bare `<Image>`:** When a field accepts any URL the user types (e.g. a cover-image input, not a curated/local asset), Next's image optimizer requires the host to match `images.remotePatterns` in `next.config.ts` — and that allowlist is typically `https`-only (see `next.config.ts`'s wildcard `hostname: "**"` under `protocol: "https"`). A plain `<Image>` will silently fail to preview any `http://` URL a user pastes, even though a raw `<img>` (or a properly configured `<Image unoptimized>`) would render it fine. `EditTripClient.tsx`'s live cover-image preview already established this pattern (`<Image fill ... unoptimized />`) — check for it before converting any other "arbitrary external URL" image spot to `next/image`.
- **A shared `styles` prop typed with named required fields won't accept a real `*.module.css` import:** Next.js infers CSS module imports as `{ readonly [key: string]: string }` (an index signature), which is not structurally assignable to an interface with specific required string properties (`{ backdrop: string; container: string; ... }`) — `tsc` rejects it even though every expected key is present at runtime. When building a shared shell component (e.g. `ModalShell`) that takes a caller's own CSS module as a prop so each caller keeps its exact existing styling, type that prop as `{ readonly [key: string]: string }` to match reality, not as a named-fields interface.
- **A shared dialog/panel shell needs a slot for content between the header and the scrollable body, not just header/body/footer:** `AttractionSearchModal`'s search bar sat outside the scrollable results list as a sibling `div`, pinned below the header. Wrapping *all* passed-in content in a single scrollable body wrapper (as a naive `ModalShell` would) makes that search bar scroll away with the results — a layout regression invisible until you trace the original DOM structure. Add an optional `beforeBody` slot (rendered between the header and the scroll container, outside it) for any modal with pinned sub-header content.
- **Barrel files can silently pull SSR-unsafe modules into an unrelated page's server bundle — audit module-scope side effects before adding a barrel export, not just types:** A shared barrel (`@/lib/index.ts`, `@/components/index.ts`) makes every export reachable from *any* import of that barrel, even if the importing file only wanted one unrelated named export. Two concrete breaks from this during `component-barrel-files`: (1) `src/lib/mapIcons.tsx` imports `react-dom/server` — barreling it broke the build for every client component importing anything else from `@/lib`, because Next.js forbids `react-dom/server` anywhere in a Client Component's module graph. (2) `CitiesMap`/`CountriesMap` run module-scope Leaflet setup (`L.Icon.Default.mergeOptions`) that touches `window` — barreling them as values broke static prerendering of `/admin` and `/analytics` (pages that import unrelated things like `IconPicker` from `@/components`) with `ReferenceError: window is not defined`, even though their actual consumers already loaded them safely via `next/dynamic({ ssr: false })` pointed at the file directly. Fix pattern: exclude the SSR-unsafe module from the barrel's *value* exports (type-only re-exports are erased at compile time and stay safe), and have its few real consumers import it directly by path — same treatment as server-only modules (`mongoose.ts`, `auth.ts`). Rule of thumb: before barreling a module, check whether it does anything at module scope beyond plain function/const declarations (imports `react-dom/server`, touches `window`/`document`, calls a library's global-mutation setup) — if so, it's a barrel exclusion candidate regardless of whether it's marked `"use client"`. `tsc --noEmit` will NOT catch this class of bug — only a full `npm run build` (checking the actual route list for prerender failures) will.
- **Populated Mongoose refs resolve to `null`, not an error, when the referenced document is deleted — guard before `.toString()`:** `Trip.findById(id).populate("ownerId", ...)` doesn't throw or omit the field if the referenced `User` no longer exists; it silently sets the populated field to `null`. Any formatter (e.g. `formatTrip` in `src/models/Trip.ts`) that assumes "populated means present" and calls `.toString()`/property access on it will throw, which a route's blanket `catch` turns into an opaque 500 — and a client that only special-cases 404/403 will blindly `res.json()` the `{ error }` body and cast it to the real type, crashing later on `undefined` fields instead of surfacing a clear error. Fix pattern used here: null-check the populated value explicitly (test for an expected populated-only field like `"name" in raw`) before touching it, drop/omit orphaned array entries (e.g. a dangling collaborator) rather than crashing, and always `console.error` the real error in the route's catch block instead of swallowing it — the generic message alone gives no signal about *which* document was orphaned.
- **Global name-only dedup on a shared entity must include the field a caller actually filters by, or reused documents go stale:** `POST /api/trips/[id]/attractions` deduped `Attraction` documents by `name` alone before reusing/linking one to a trip. Because attractions are intentionally shared/reused across trips (see the entry above), an attraction created under one trip's country could get silently reused for an unrelated same-named place, keeping the *first* document's `country` value forever — which then made it invisible to any other trip's exact-match `?country=` search. Fix: scope the dedup lookup to `{ name, country }`, not `name` alone. Don't "fix" this by overwriting the shared document's field on every reuse instead — that corrupts the data for every other trip already linked to the original. This was a real, legitimate bug found by code review, but turned out **not** to be the cause of the user-reported "attraction shows as though it doesn't exist" — see the auth-header entry below for the actual cause. Keep both fixes; they're independent and both correct.
- **A service function silently missing its `Authorization` header only breaks results for a subset of data — easy to miss without a real repro:** `searchAttractionsByCountry` (`src/services/attractions.service.ts`) never sent the caller's token, even though the caller (`AttractionSearchModal`, rendered from `TripDetailClient.tsx`) had one available via `useAuth()`. `GET /api/attractions` treats a tokenless request as fully unauthenticated, which flips its private-trip visibility filter to "only public trips are accessible" — so *any* attraction linked only to a private trip became invisible to search, even to that trip's own owner. This is exactly the kind of bug that code review alone won't catch: the endpoint's filter logic was correct and well-tested in isolation (verified via direct authenticated `curl`), and the modal, component, and search flow all looked fine reading top-to-bottom — the break was purely "this one call site forgot to attach the token," invisible without either grepping every `fetch(`/service call for a missing `Authorization` header, or reproducing with a real logged-in session against real data. Fix: thread `token` through as an explicit prop (`AttractionSearchModal` → `searchAttractionsByCountry`) rather than assuming a service function has access to auth context.
- **`next/image`'s default `loading="lazy"` deadlocks with a "hidden until loaded" preview pattern — the image never starts loading because it never has a layout box to intersect:** A preview that starts `display: none` and only reveals via `onLoad` (`CoverImageField.tsx`) looked like a classic "cached image, `load` event doesn't refire" bug (see below for that real-but-secondary issue) — but the actual, confirmed-via-browser root cause was that Next's `<Image>` defaults to lazy loading, which uses `IntersectionObserver` under the hood. An element with `display: none` has no layout box, so it can never be reported as intersecting the viewport, so the lazy loader never triggers the fetch at all — confirmed in a real browser: `el.complete` stayed `false` and `el.currentSrc` stayed `''` (no request ever fired) for 3+ seconds on an always-visible field with a pre-filled value (the Edit Attraction flow, where `CoverImageField`'s `value` is non-empty on the very first render). Fix: set `loading="eager"` on the `<Image>` (or `priority` if it should also preload). The secondary, real issue (an already-*fetched*-but-cached image not re-firing `onLoad`) still matters and is handled by checking `.complete` in a ref callback (next entry) — but it's not the reason the preview was "always" blank; the lazy-loading deadlock is. **Lesson: when a plausible root cause explains the symptom on paper but the fix doesn't resolve the user's actual repro, don't stop at the first theory that fits — reproduce in a real browser (`el.complete`/`el.currentSrc`/network tab) before concluding the bug is fixed.**
- **`<img>`/`next/image` `onLoad`-only preview reveal breaks for cached images — and the standard fix collides with the `react-hooks/set-state-in-effect` lint rule:** A preview pattern that starts hidden (`display: none` by default) and only reveals via `onLoad`/`onError` handlers silently stays hidden forever if the image is already `complete` by the time the listener attaches (common for a URL pasted twice, or already cached from elsewhere) — the native `load` event doesn't refire. The naive fix (`useEffect` that checks `imgRef.current?.complete` and calls `setState`) trips this repo's `react-hooks/set-state-in-effect` rule, which flags *any* synchronous `setState` inside a `useEffect` body. Working pattern instead: derive the "loaded" boolean from state (`loadedUrl === value`, not a separate boolean + reset effect) and check `.complete` inside a **ref callback** (not an effect) combined with `key={value}` on the image so the callback re-fires for every new URL. Ref callbacks aren't subject to this lint rule. (This alone did not fix the user's reported bug — see the `loading="lazy"` entry above for the actual primary cause found after this fix was verified insufficient in a real browser.)
- **Adding hooks to a previously-hookless shared component can break unrelated Server Component pages via the barrel file:** `CoverImageField.tsx` had no `"use client"` directive because it didn't need one (no hooks, just props/JSX) — safe to re-export as a value from the shared component barrel even though a few of its consumers are Client Components. Adding `useState`/`useCallback` to fix the caching bug above made it a hook-using module with no client boundary of its own, which broke a *different*, unrelated Server Component (`src/app/explore/page.tsx`) that only imported some other export from the same barrel — Next.js resolves the whole barrel's module graph, and any hook-using file reachable through it without `"use client"` fails the whole build with "importing a module that depends on `useState` into a Server Component." Rule of thumb: any time a shared component starts using hooks for the first time, add `"use client"` to it in the same change, and re-run `next build` (not just `tsc`) to catch barrel fallout — `tsc --noEmit` does not catch this class of break.
- **Deleting an API route file leaves a stale `tsc` error until `.next` is cleared:** After deleting `src/app/api/trips/[id]/expenses/route.ts` (full feature removal), `npx tsc --noEmit` failed with `Cannot find module '../../src/app/api/trips/[id]/expenses/route.js'` — not a real code error, but Next.js's auto-generated `.next/types/validator.ts` still referencing the now-gone route file from a prior build. `rm -rf .next` (or just running `next build`, which regenerates it) clears this. Don't chase this as a real type error when it follows a route-file deletion.
- **"First-encountered order while iterating a sorted array" is not the same as "sorted order" for the group keys themselves:** `useAttractionTypes.ts` built its `categories: string[]` output by pushing each category name the first time it was seen while iterating `types` (already sorted by name via the API). This looked safe but wasn't — the array being iterated is sorted by *type* name, not *category* name, so the first type alphabetically can belong to any category, putting that category first regardless of its own name. Whenever a derived "unique keys in order" list needs to be sorted by something other than the exact sort key of the array being folded, sort the derived key list explicitly (`Object.keys(map).sort(...)`) rather than assuming iteration order carries over.
- **"Pick an existing shared document, but this trip needs its own copy of some fields" — use a schedule-entry override, never write onto the shared document:** Residences (and any other subtype reused across trips via `existingAttractionId`) can have fields that are conceptually per-trip (check-in/out dates, price) but that live on the shared `Attraction` document for historical reasons. Writing a new trip's values onto that shared document silently corrupts every *other* trip that also links to it. Fix pattern: add the field to `IScheduleEntry` (`Trip.schedules`, already used for `plannedDate`/`plannedTime`), write it there instead of onto the document when resolving via `existingAttractionId`, and have `formatAttraction(doc, schedule)` prefer `schedule.field ?? doc.field` so old data (no override yet) keeps working unchanged. Before applying this pattern anywhere, grep for other write paths to the same fields — `PUT /api/attractions/{id}` (the generic edit-attraction route) bypasses the schedule mechanism entirely and will still corrupt shared data if a user edits a reused document's dates directly; that's a separate, real gap worth fixing in its own task, not blocking scope creep into whichever task first surfaces it.
- **The `unoptimized` fix for arbitrary user-pasted image URLs isn't just for cover images — check every field that stores a free-text URL:** The documented fix (`next/image` + arbitrary pasted URLs → use `unoptimized`) had only been applied to `EditTripClient.tsx`'s cover-image preview. `Attraction.photoUrl` is the same class of field (free-text URL, not a curated/local asset) but two other render sites — `AttractionDetailModal.tsx`'s photo and `TripDetailClient.tsx`'s attraction-row thumbnail, both via `ImageWithSkeleton` — still used a bare `<Image>`, so any pasted `http://` URL (e.g. a Google Images thumbnail proxy link) failed with "hostname not configured," and even a same-host `https://` URL not covered by `next.config.ts`'s `remotePatterns` would fail the same way. When a fix pattern is established for one field, grep for every other field of the same *kind* (free-text URL input) rather than assuming it's a one-off — `grep -rn "photoUrl" src` immediately surfaced both other sites.
- **Running `next build` while `next dev` is live against the same project corrupts the dev server's route manifest:** Verifying a change with a full production build (needed to catch barrel/SSR issues `tsc` misses) while the user's own `npm run dev` is still running against the same `.next` directory causes previously-working routes to start 404ing in the browser (e.g. `GET /trips 404`) even though the code and the build itself are both correct. This happened twice in the same task. Fix is operational, not code: after running `next build` for verification, check for and restart the project's `next dev` process (`Get-CimInstance Win32_Process -Filter "name = 'node.exe'"` filtered to the project path on Windows) rather than treating the resulting 404 as a real regression to debug.
- **A new `.utils.ts` hook file needs `"use client"` the moment it's added to the barrel, not just when it "feels client-side":** `Pagination.utils.ts` (a hook, `usePagination`, using `useState`/`useMemo`) was written without a `"use client"` directive — easy to miss because `.utils.ts` files in this codebase are usually plain pure functions. `tsc --noEmit` passed; only `next build` caught it, failing with "importing a module that depends on `useState` into a React Server Component module" once a Server Component page reachable through the `@/components` barrel touched it. Same root cause as the barrel/SSR-unsafe-exclusions entry below, but the trigger here is a *new* file, not an existing one gaining hooks — check every new hook-bearing file for the directive before barreling it, not just files being retrofitted with hooks.
- **`fdprocessedid` hydration mismatch on a button is a browser-extension false positive, not an app bug:** A form-filler extension (LastPass/Bitwarden-style) injects a `fdprocessedid` attribute onto interactive elements (buttons, inputs) before React hydrates, which React then reports as a real server/client mismatch. Confirmed via the dev-overlay diff (`- fdprocessedid="09v59d"` on `ThemeToggle`'s button, nothing else differed) rather than assumed — check the actual diffed attribute before treating any hydration warning as a real bug. Since it's cosmetic console noise with no functional impact, silence it with `suppressHydrationWarning` on the specific element rather than restructuring app code to "fix" something that isn't broken.
- **A module-level `invalidate*Cache()` that only nulls the cache doesn't refresh already-mounted components — it needs a subscriber list:** `useAttractionTypes`/`useAttractionCategories`/`useMoodTags` each cache fetched data at module scope with an `invalidate*Cache()` export, but their `useEffect(() => {...}, [])` only reads the cache once on mount — clearing the cache alone does nothing for a component already on screen. This is exactly why `AdminClient.tsx` previously called `window.location.reload()` after every mutation: it was the only way to force a re-fetch. Removing the reload (e.g. to show a toast instead of a full page reload) silently breaks list refresh unless the hook also exposes a way to be told "reload now" — pattern used: a module-level `Set<() => void>` of subscriber callbacks that each mounted hook instance registers/unregisters via its effect's cleanup, and `invalidate*Cache()` calls every subscriber after clearing the cache.
- **Never compare a possibly-populated ref field with `.toString() === someIdString` — `Document.prototype.toString()` returns an `inspect()` debug dump, not the id:** If a query calls `.populate("ownerId", ...)` (e.g. for avatar display) and *later* code does `doc.ownerId.toString() === userId` to check ownership, that comparison silently always fails once the field is populated — Mongoose's `Document.prototype.toString` returns a multi-line `util.inspect()`-style string of the whole document, not the plain ObjectId hex. This bit `src/app/api/trips/[id]/route.ts`'s `GET` handler: after `.populate("ownerId"/"collaborators.userId", ...)` was added for avatar display, the pre-existing `isOwner`/`isCollaborator` checks kept using raw `.toString() ===`, so the real owner of a private trip got a 403 "This trip is private" — invisible until a separate crash earlier in the same handler (see the entry above) got fixed and execution actually reached this check. Fix: a small `resolveRefId(ref: unknown): string | null` helper that unwraps either a raw `ObjectId` or a populated document (checks for `_id`) to a plain id string, used for any identity comparison on a field that *might* be populated. Rule of thumb: grep for `.toString() === ` near any query that also calls `.populate()` on the compared field, in this file and any other route touching the same model — this class of bug doesn't show up until someone with real ownership actually hits the code path, so it can sit unnoticed for a while.
